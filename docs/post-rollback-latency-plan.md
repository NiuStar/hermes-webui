# 回滚后延迟定位与优化实施方案

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task. 本次仅诊断与方案，不授权部署。

**Goal:** 消除会话展示对模型元数据刷新等待的依赖，并按细分耗时优化长会话读取，保持历史显示与恢复语义。

**Architecture:** 展示读路径使用有来源、与配置版本绑定的模型元数据；刷新与正文读取解耦。长会话先分段计时再优化已证明的热点，不以扩大缓存或数据库迁移代替定位。

**Tech Stack:** 现有 Python WebUI、SQLite、JSON sidecar；沿用 `.10` 部署，不另建测试部署环境。

## 2. 已证实与未证实

### 已证实：小会话存在模型/上下文刷新门控的额外同步等待

同一生产进程、相同正文请求，仅切换resolve_model即从秒级降到约60ms。现有SLOW日志：小会话total2026.1ms，get_session8.4ms、model_resolve18.3ms、compact1939.5ms、redact59.2ms、json_write0.8ms。大部分等待不是数据库读取，也不是JSON发送。

生产 `api/routes.py:13781–13801` 在compact计时区间调用 `_resolve_context_length_for_session_model`，受 `not persisted_cl OR resolve_model` 门控；它进入Agent `get_model_context_length`，该函数具备远端模型元数据探测路径。因此日志的compact不能解读为单纯压缩或合并。

边界：实际远端socket调用、具体上游地址及等待分布尚未动态追踪，不能宣称已证明某上游服务超时。resolve_model=0也不是通用修复：无persisted_cl时仍可刷新，并可能改变模型信息展示。

### 已证实：长会话有独立于上述开关的残余瓶颈

关闭resolve_model仍约1.89–2.36秒。代表日志总2215.1ms，get_session72.5ms，compact2129.7ms，redact10.6ms，json_write2.1ms。compact区间还包含展示合并、窗口处理、Session.compact和todo派生。

尚未证明其中哪个函数占主导。源码存在合并后 `_cache_json_size_bytes` 全量编码及超预算拒绝缓存的可能路径，但本次无动态证据证明它就是2秒热点，不能直接以增加缓存解决。

### 本次没有完成的验证

未重启服务、清缓存或制造强制冷启动，因此没有复现先前18秒冷请求；未测真实浏览器渲染；未将GET自带的历史housekeeping断言为绝对零写入。没有修改生产代码、安装/附加profiler、创建对话或执行数据库写脚本。

## 3. 分步方案

### P0：让正文读取不等待模型元数据联网刷新

涉及 `api/routes.py`、必要时 `api/config.py`，新增 `tests/test_session_display_metadata_nonblocking.py`。

1. 先写失败测试：模型元数据探测抛错/阻塞时正文GET必须不调用它；覆盖persisted_cl缺失、配置修改、跨profile、同名模型不同provider/base_url、显式模型选择。
2. 将展示模型身份解析与上下文窗口刷新拆开。展示优先明确配置、同配置签名的已持久值/缓存；未确认时标记unknown或stale，不将推测值冒充权威。
3. 使用有界后台刷新、单请求合并、超时及失败退避；缓存键包含profile、provider、model、endpoint及配置版本，禁止跨账号串用。不在缓存键/日志存明文密钥。
4. 不改变真实推理、压缩阈值和发送时的权威校验；展示降级不等于放宽运行安全边界。
5. 先运行新增测试，再复跑现有模型路由、上下文窗口、session分页和恢复测试。P0独立提交、独立验收，不夹带旧缓存候选。

### P1：细分compact，再改长会话实际热点

涉及 `api/routes.py`、`api/request_diagnostics.py`；按定位结果才决定 `api/models.py` 或合并工具是否修改。

1. 添加低开销、可关闭、无正文/密钥的计时：sidecar/父链加载、SQL读取、签名、cache命中/拒绝原因、merge、缓存字节计量、窗口裁剪、context刷新、Session.compact、todo、redaction、序列化/写出。记录行数、字节和请求关联ID。
2. 本地测试验证计时边界正确；经批准随最小可回滚版本在既有 `.10` 路线验收，不另建测试部署环境。
3. 用相同三个会话串行复测。只有热点证据成立才选择下述分支：
   - 若全量merge主导：优先减少重复计算和复用身份/签名可靠的结果；不得改变现有去重、分支和截断语义。
   - 若超限缓存计量主导：避免每次为确定无法缓存而全量编码，预算必须真实有界；不能以无界缓存换速度。
   - 若分页后仍做全历史派生主导：将纯展示派生后移到窗口范围；先证明工具关联、todo及全局坐标兼容。
   - 若冷sidecar解析主导：考虑可重建、来源签名绑定的展示索引/物化视图；不可直接尾读JSON丢失全局坐标。此路线需单独设计审查，未获准前不实施。
4. 每次只改一个热点，保留对照证据；不要把函数基准代替正式HTTP结果。

### P2：正式验收与失败回滚

以下是建议验收目标，不是已达成绩：

- 相同入口、参数、profile及消息版本下，每组至少20次串行热请求；小会话正文HTTP p95≤200ms；长会话尾页p95≤800ms。metadata p95≤100ms。
- 冷首屏单列：经用户允许的受控重启后，长会话首个尾页目标≤2秒；不清OS缓存，不删除历史文件。不获重启许可则标记冷门禁未测。
- 真实浏览器检查首屏、滚动翻页、工具卡片和恢复；记录网络/解析/渲染，不将宿主本机网络成绩当用户体验成绩。
- 全部分页窗口正文哈希、顺序、总数、工具关联保持基线一致；测试缺上下文值、改配置、压缩、编辑、再生成、分支、恢复及并发写入时失效。
- 对未知模型值不得伪造；对来源签名不确定的缓存失败关闭。
- 控制RSS及缓存总预算，观察健康请求在正文读取期间是否排队；不进行未经许可的压力洪泛。
- 性能或完整性任一不达标即回滚到保留journal解码器的 `af654091` 兼容版本，读回镜像/健康及历史窗口；严禁回到缺新解码器的旧版本。

## 4. 非本轮范围

不换数据库，不迁移schema，不删除inactive历史，不停sidecar正文双写，不调整或清理历史保留数据，不另建测试部署，不迁移微信/cron/workspace。旧18秒冷请求及浏览器体验仍是明确未决项。
